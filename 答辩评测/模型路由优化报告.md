# 模型路由优化报告

## 目的

模型只参与语义候选建议，确定性引擎负责计算、裁决和写回 Office 文件。优化前，Agent 会把所有未确认论断整批交给 API，并用 API 结果覆盖本地结果，导致模型在规则已经唯一确定的样本上重复工作。

## 当前路由

```text
规则唯一候选 / 已解析的增长率、排名、阈值、图表
    -> 直接进入人工确认，不调用模型
规则多候选
    -> 本地 BGE reranker 排序
    -> 低置信或拒答才升级 API
规则零候选
    -> API 语义召回；失败则人工确认
所有来源
    -> 人工确认后，确定性引擎重新核验并修复文件
```

API 请求在项目内按最多 40 条困难论断分批，`agent.model_routing.api_batches` 会记录实际批次数。不同文档组的离线评测不能直接合并事实表，因为事实 ID 和口径必须保持组内隔离；因此跨组报告只给理论批次数下限，不把它当成实测延迟。

## 评测结果

评测文件：`model_routing_metrics.csv`、`model_routing_report.json`、`model_routing_comparison.svg`。当前 180 条是程序化夹具，30 个文档组，不能称为人工行业真值。

| 方案 | Top-1 | 错误关联率 | 歧义拒答率 |
|---|---:|---:|---:|
| 纯规则 | 100% | 0% | 100% |
| 全量本地 reranker | 40% | 0% | 100% |
| 全量 API | 60% | 33.33% | 0% |
| 分层路由 | 100% | 0% | 100% |

纯规则的 Top-1 只在 `gold_action=link` 的样本上计算，因此不能单独代表安全性；它会把歧义样本错误关联。分层路由把歧义交给人工，从而消除错误自动关联，代价是拒答率上升。

当前这套合成评测中，多候选样本主要是增长率、阈值和歧义夹具，复合论断本来就应由确定性规则处理，歧义样本本来就应人工确认。因此本批数据证明了“调用范围和安全闸门”有效，不能证明 reranker 已经提升了中文同义表达的召回率。后续应加入真实中文改写样本，再单独评估本地 reranker 的增量。

## 答辩可用表述

> 我们没有让模型接管计算和写回，而是用评测结果决定模型在哪些样本出场。规则已唯一确定的 83.3% 论断不调用 API；模型只处理规则无法确定的候选，低置信结果转人工。这样全量 API 的错误关联被消除，系统仍保持可解释、可审计和离线可用。

外部程序化 holdout 另有 BGE ONNX Top-1 `96.18%` 的结果，中文 BERT v2 为 `41.32%`；这些结果仍需在报告中标注为程序化标签，不能替代人工复核。
