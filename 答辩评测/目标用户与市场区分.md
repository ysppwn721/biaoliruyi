# 目标用户与市场区分（PPT 素材）

> 用途：答辩 PPT「用户定位」与「竞品区分」章节的素材
> 原则：只写**可验证的事实**，不做无法自证的量级承诺

## 一、竞品现状：数据一致性治理已有商业方案

报告数字与源数据不一致，不是没人做过。市面已有成熟产品，且都已用上 AI：

| 产品 | 定位 | 形态 | 用户 |
| --- | --- | --- | --- |
| **UpSlide** | 财务与报告团队的质量保证 | Microsoft Office 插件 | 企业金融/报告团队，按用户订阅 |
| **CCH Tagetik Intelligent Disclosure** | 企业披露管理 | 企业级平台 | 上市公司财务与合规部门 |
| **WPS 365** | 表格跨表联动 | 金山生态内公式联动 | 个人/企业，但**仅限表格之间** |

**它们的共同特征**：

- 都面向**企业**，需企业采购、IT 部署与运维
- 都**依赖 Microsoft Office 或自建生态**
- 一致性判定**依赖云端大模型**（单一路径，无本地判定能力）

> UpSlide 有 AI Consistency Check，CCH Tagetik 提供 AI 驱动的披露文档校验。
> 这说明：**"用 AI 检查报告数字"已不是空白，不能宣称首创。**

> **一处必须说准的事实**：UpSlide 并非"把文档上传到云端"。
> 其官方文档写明：**工具执行在本地，MCP server 不直接访问用户文档，文档留在用户机器上**；
> 送到云端的是 **prompt 与用户信息**，判定由企业专属 Azure AI Foundry 上的 OpenAI 模型完成。
> 因此**准确的说法是"判定依赖云端模型"，而不是"文档上传"**——说错会被官方文档反证。

## 二、模型架构对比（本项目的架构区分点）

这一节是"多模型协同"与"单一云模型"的差异，全部有据可查。

### UpSlide 的模型架构（引自官方文档）

```
Word/Excel/PPT 插件  →  HTTPS(TLS 1.2)  →  企业专属 Azure AI Foundry  →  OpenAI 模型
      本地                                       云端                      云端
```

官方 AI 治理文档原文要点：

> **"Data sent: User Information, prompt. Data retrieved: OpenAI response."**
>
> 每个 AI 功能（AI Assistant、AI Glossary、AI Consistency 等）**各有独立基准，必须分别通过**；
> 一个模型可能对功能 A 有效、对功能 B 无效，则**只允许用于功能 A**；
> 每次发新版重跑测试，标准随技术进步提高，**旧模型会被淘汰**。

**结论：单一路径、单一模型族、全云端，无规则引擎兜底、无本地模型。**

> ⚖️ **公平说明**：UpSlide 的**模型治理纪律明显强于本项目**（逐功能独立基准 + 版本回归 + 主动淘汰）。
> 这一点应当学习，而不是拿来当差异。本项目已按其思路做**分层评测与归因**。

## 三、成本与泛用性：限定到证据能支撑的范围

### ✅ 可以说：上游调用成本（含实测数字与限定条件）

**度量口径**：单份含 280 条论断的报告（真实长文夹具），同一模型下的 token 用量。
**为什么不看价格、只看 token**：若两套方案用同一模型，**上游成本比 = token 量比**，
这与具体厂商定价无关，是更稳的论证。

| 模式 | 调用次数 | 输入 token | 输出 token | 成本/份（按 DeepSeek 官方价折算） |
| --- | --- | --- | --- | --- |
| 全量 API | 25 | 19,724 | 10,288 | 0.0609 元 |
| **分层（仅零候选升级）** | 21 | 9,810 | 1,584 | **0.0161 元** |
| 变化 | −16% | **−50%** | **−85%** | **−73.5%** |

**深层原因**：费用由输出 token 主导（输入 1 元/M、输出 4 元/M）。
分层把 83% 的论断挡在本地，**输出 token 降 85%**，所以总成本降幅远大于调用次数降幅（16%）。

按 DeepSeek 官方价（输入 1 元/M、输出 4 元/M，均未命中缓存）：

```
1,000 份/年 ：    60.88 元 →   16.15 元   省   44.73 元
10,000 份/年：   608.76 元 →  161.46 元   省  447.30 元
100,000 份/年： 6,087.60 元 → 1,614.60 元  省 4,473.00 元
```

> ⚠️ **必须同时说清的限定条件（否则会被追问）**：
>
> 1. **这是上游调用成本，不是产品售价**。本项目未发布定价、无订阅体系，
>    **不能声称"我们比 UpSlide 便宜 X%"**——那是终端价格，无从比较。
> 2. **单份报告的绝对金额很小**（6 分钱 → 1.6 分钱）。在小规模下，
>    **"省 73.5%"听起来大，实际只省 4 分钱**。不要用小基数放大比例。
> 3. 当规模达到万份量级时，节省仍是数百元级别，**不构成商业壁垒**。

### ✅ 真正值钱的不是省钱，是"不产生这笔钱"

上面的算法只对**零候选那 48 条**收费。而关键事实是：

**83% 的论断（232 / 280）根本不需要联网，判定在本机完成。**

| | 企业级产品 | 表里如一 |
| --- | --- | --- |
| 判定是否必须联网 | **是，判定走云端模型** | **否，83% 本地完成** |
| 数据出域 | prompt 与用户信息出域 | **83% 完全不出本机** |
| 离线场景 | 不可用 | **可用** |
| 前置条件 | 有 Office + 有网络 + 有采购 | **三者皆不需要** |

**这条对特定场景是"能不能用"的问题，不是"贵不贵"的问题**：

| 场景 | 云端方案 | 本方案 |
| --- | --- | --- |
| 党政机关内部报告 | 数据不能出域，**直接出局** | ✅ 可用 |
| 金融机构未公开数据 | 需专门审批与专属实例 | ✅ 可用 |
| 高校科研未发表数据 | 存在合规顾虑 | ✅ 可用 |
| 无网络环境（内网/现场） | **不可用** | ✅ 可用 |
| 规模极大（十万份级） | 成本与数据暴露面同步放大 | ✅ 大部分本地消化 |

> **答辩口径**：**不要说"我们更便宜"，要说"很多场景下我们不需要这笔费用，
> 也不需要把数据送出去"**。前者是可被追问的定价问题，后者是架构事实。

### ⚠️ 关于模型本身的价格：不构成本项目的差异

有两点必须澄清，否则会被认为在偷换概念：

1. **本项目改用国内模型（如 DeepSeek Flash）会显著更低**——
   但那是**模型选型差异**，不是"多模型架构带来的节省"。混在一起讲是错的。
2. **UpSlide 跑在企业专属 Azure AI Foundry 上**，其模型单价
   **未在公开定价页静态披露**（Azure 定价页由脚本动态渲染，未能取得可比数字）。
   因此**本项目不做跨厂商单价对比**，只做同模型下的 token 量对比。

**结论：成本优势的准确表述是"上游用量降 50%–85%、且 83% 不出本机"，
而不是"我们比竞品便宜多少"。**

### ✅ 可以说：泛用性（四条架构事实）

| 维度 | 企业级产品 | 表里如一 |
| --- | --- | --- |
| **Office 依赖** | 必须安装 Microsoft Office | **不需要，直接读写 OOXML** |
| **联网要求** | 判定必须联网 | **可离线** |
| **平台约束** | 绑定 Windows + Office 生态 | **Windows / Linux 均可，提供两种安装形态** |
| **程序化访问** | 以插件交互为主 | **MCP 只读工具接口**（7 个工具），可被外部 Agent 调用 |
| **取得成本** | 企业采购流程 | **下载即用** |
| **来源审计** | 闭源 | **完整源码可审 + 232 项自动化测试** |

**泛用性的准确表述**：不是"功能更多"，而是**"在更多环境下可用"**——
企业产品要求"有 Office + 有网络 + 有采购预算"三个前提；
本项目**三个前提都不需要**。

> 行业专用产品（披露管理）本身即面向企业合规流程，其"专用"是定位选择，不是缺陷。
> 因此**表述为"适用面不同"，而不是"我们比它们更好"**。

## 四、我们的区分：架构事实，不是定位口号

| 维度 | 企业级产品 | 表里如一 | 性质 |
| --- | --- | --- | --- |
| **运行依赖** | 必须安装 Microsoft Office | **直接读写 OOXML，不装 Office 也能运行** | ✅ 架构事实 |
| **判定位置** | **云端模型判定**（文档本地、prompt 上云） | **本地即可判定**（规则 + 本地模型覆盖 83%） | ✅ 架构事实 |
| **费用** | 企业订阅（按用户） | **无订阅体系**（本项目未定价） | ⚠️ 仅陈述事实 |
| **成本结构** | 需 IT 采购与运维 | **单机运行，无需 IT 资源** | ✅ 事实 |
| **判定方式** | AI 黑盒判定 | **确定性计算（Decimal + 单位/口径约束）** | ✅ 可复现 |
| **能力边界** | 指出"可能不一致" | **最小改动修复 + 重新读取文件复核** | ✅ 可验证 |

**关键差异是最后两行**：

- 企业产品的 AI 校验只能给出"这里可能不一致"；**审计场景需要的是可追溯的证据**，而不是模型判断
- 企业产品**发现问题即止**；表里如一会**按字符锚点做最小改动，并重新读取生成的文件独立复核**

## 五、目标用户：三段式

### 核心用户（主推）

**学生、科研人员、高校与科研团队**

**为什么最匹配**——他们天然产出**文档三件套**：

| 材料 | 作用 | 与本系统的关系 |
| --- | --- | --- |
| **Word 报告** | 实验报告、论文、结题报告、成果报告 | 正文含数值结论 → **被核验对象** |
| **Excel 数据表** | 原始数据、统计结果 | **事实来源** |
| **PPT** | 开题、中期、答辩、汇报 | 含结论与图表 → **被核验对象** |

**典型痛点**：

- 数据复核后，报告与幻灯片里的数字要**逐篇手动改**，容易漏
- 「本期销售额较上期增长 25%」这类结论，**数据一变就要重算**
- 答辩稿与论文数据**互相不一致**，自己看不出来

### 扩展用户

**中小企业中需要对外提交材料的人**

- 项目申报、政府汇报、投标文件、年度总结
- 特点：有 Word 报告 + Excel 数据，但没有企业 IT 资源，也不会为核对数字买企业级订阅

### 未来方向（需要新增能力，暂不计入现有范围）

**纯表格场景（如小微商户的进销存对账）**

- 需求真实存在：多张表之间核对、月度与总账比对
- **但形态不同**：这类场景是「表 vs 表」对账，**没有含数值结论的 Word 正文**
- 本系统的核心能力（从 Word/PPT 正文定位数值论断）在此场景**用不上**
- 若要覆盖，需新增「表格对账」入口——底层已有 `engine` 的确定性计算与 `graph` 的依赖图，但**尚无对应产品入口**

> **答辩建议**：把这一条放在"未来规划"，不要当成现有能力讲。
> 若被问"能否用于小卖店"，如实回答："需要新增表格对账入口，当前版本聚焦含叙述文字的文档。"

| --- | --- | --- |
| 事实关联 Top-1 | 0.868 | **1.000** |
| 错误关联率 | 0.011 | **0.000** |

对"数据不出本机"有要求的场景（党政、金融、科研未公开数据），**云端 SaaS 直接出局**，这是架构决定的结果。

## 七、答辩口径（建议原话）

> 报告数字的一致性治理已有商业方案，如 UpSlide、CCH Tagetik，但它们都面向企业，需要采购订阅、依赖 Microsoft Office。
>
> 表里如一走另一条路：**不装 Office 也能运行、无订阅、判定可在本地完成**，用确定性计算而非模型猜测给出判断，并且**不只指出问题，还做最小改动修复并重新读取文件复核**。
>
> 我们的用户是 **学生与科研人员**——他们天然同时维护 Word 报告、Excel 数据与 PPT 汇报，数据一变就要逐篇手动改，正是这套系统要解决的问题。

### 若被问到成本

> 我们不与竞品比价格（本项目没有订阅体系）。
> 可比的是**同一模型下的上游用量**：单份 280 条论断的报告，
> 全量调 API 需 19,724 输入 + 10,288 输出 token；
> 分层方案只需 9,810 + 1,584，**输入降 50%、输出降 85%**。
> 根本原因是**83% 的论断由本地规则与本地模型完成，根本不到 API**。
> 更好的说法不是"我们省钱"，而是**"很多场景下我们不需要产生这笔费用，也不需要把数据送出去"**。

### 若被问到模型架构

> 我们的模型层是**分层路由**而非单一路径：
> 规则先召回并收紧候选，多候选交本地 ONNX reranker 排序，只有零候选或低置信才升级到 API。
> 这套架构的价值已实测：**错误关联率 0，输出 token 降 85%**。
>
> 我们参考了 UpSlide 的模型治理思路——**每个 AI 功能独立基准、逐版本回归**——
> 并对本项目做了分层归因评测。这一纪律是从竞品身上学来的。
