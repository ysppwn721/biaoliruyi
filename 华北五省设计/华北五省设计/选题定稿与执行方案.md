> **主选：校园政策与办事流程智能体**
> 拟定题名：**校园政策智办——基于证据链与流程状态机的办事智能体**
> 定稿日期：2026-09-13 ｜ 距校内系统提交（9/19）6 天 ｜ 距官网最终提交（10/8）25 天
> 赛道：方向一（大模型与智能体应用赛道）

## 一、先处理"缺少资源"留下的短板

选政策方向**逻辑正确**：它所需的资源（公开规章、办事指南、身边真实用户）不依赖任何外部单位授权，是"无资源"约束下的最优解。

但必须正视一点：**这个方向原本的差异化是"本校真实资料 + 真实用户"。没有官方授权，如果不主动补齐，作品会退化为通用问答，与往届《接诉即办问答系统》（二等奖）同档。**

### 不用授权也能拿到的真实资源（9/14—9/15 两天做完）

| 需要的东西 | 不用授权怎么拿 | 归属 |
|---|---|---|
| 政策与办事文件 | 学校官网、学生手册、教务处/学生工作部/资助中心网页的**公开**通知与办事指南 | 公开信息，可引用，标注来源与发布日期 |
| 真实用户 | 身边的同学/室友（真实身份、真实诉求，非扮演） | 自己的社交网络 |
| 真实痛点证据 | 找 5—8 位同学各问一句"你办过哪件事、卡在哪一步、跑了几趟" | 一手访谈记录，写进设计文档"需求分析" |
| 业务流程验证 | 学生工作部/资助中心/教务处**窗口咨询**（打一个电话或去一次即可，不需要授权） | 口头确认即可用于校验流程正确性 |

**红线**：只用公开文件，**不要使用任何内部文件、通知转发件、带个人信息的名册**。这类材料一旦进入作品，既涉密又涉隐私，是作废级风险（大赛明确"侵犯他人知识产权等作品视为无效参赛作品"）。

**成果要求**：9/15 下班前必须拿到 ①≥8 份公开政策/办事文件 ②≥5 份真实用户访谈记录。这两样是设计文档"需求分析"章节的唯一支撑，也是答辩时"我们做了真实调研"的证据。

## 二、定第一个办理事项：奖助学金 / 家庭经济困难学生认定

**为什么选它**（按我们的赛道判据逐条对齐）：

| 判据 | 该事项表现 |
|---|---|
| 有硬截止时间 | ✅ 每学年固定窗口，错过即等一年 → 痛点真实且紧迫 |
| 材料清单长且易错 | ✅ 认定表、证明、盖章件、银行信息等，缺一项即退回 |
| 政策会变 | ✅ 认定标准与材料要求逐年调整 → **版本治理与冲突检测能自然出场** |
| 流程多部门 | ✅ 学生 → 辅导员 → 学院 → 资助中心，天然是状态机 |
| 资格条件可程序化判断 | ✅ 年级/学籍/户籍/家庭情况等结构化字段 → 可算，不是模型"感觉" |
| 可验证性 | ✅ 每条结论回指条款号；每个材料项回指办事指南原文 |
| 思想性与社会价值 | ✅ 直接对应"应助尽助"与资助公平，是政策明确导向 |
| 合规低风险 | ✅ 只涉及公开规则与用户自己填报的信息，不涉第三方隐私 |

**备用事项**（主事项若卡住可换）：毕业生离校手续办理、学籍异动（休学/复学/转专业）、校园卡与证明办理。

## 三、系统设计：核心不是 RAG

这是本方案最重要的一条判断：

> **RAG 只是取数层。系统主干必须是"政策版本治理 + 流程状态机 + 材料闭环"。**

理由：RAGFlow、Dify、MaxKB、FastGPT 等开源件已把 RAG 问答门槛压到趋零，对手两天能搭出同档问答。**评委唯一无法复制的是业务机制**，所以主干必须自研。

### 分工

| 层次 | 来源 | 说明 |
|---|---|---|
| 文档解析 + 检索 | **RAGFlow（Apache-2.0）** | 处理公开PDF/Word/网页，出检索结果 |
| 智能体编排 | **LangGraph（MIT）** | 状态、条件分支、人工审核中断、重试 |
| **政策版本治理** | **自研** | 文件表 + 条款表 + 生效期 |
| **冲突检测** | **自研** | 同事项多版本条款比对，冲突时拒绝自动裁决 |
| **身份—事项—材料匹配** | **自研** | 结构化字段规则引擎 |
| **流程状态机** | **自研** | 事项阶段推进与回退 |
| **材料闭环与缺项检查** | **自研** | 逐项上传/确认 + 缺项检出 |
| **引用校验与审计日志** | **自研** | 输出前逐条校验锚点，无锚点不出结论 |

**只用 MIT / Apache-2.0 依赖进代码库**，其余（Dify、FastGPT、MaxKB、Open WebUI、OpenResume 等）仅作设计参考、不进仓库——这直接决定"原创性"叙事能不能讲干净。

### 数据模型（自研部分的核心，设计文档要写清）

```
policy_document  政策文件：id, 标题, 发文单位, 文号, 发布日期, 生效期起, 生效期止, 状态, 来源URL
policy_clause    条款：id, 文件id, 条款号, 正文, 适用主体, 涉及事项, 生效期, 是否废止
matter           办事事项：id, 事项名, 主管单位, 办理阶段定义, 是否线上可办, 办理入口URL
material_spec    材料规范：id, 事项id, 材料名, 是否必需, 格式要求, 份数, 是否需盖章, 依据条款id
case             办件：id, 用户id, 事项id, 当前阶段, 建档时间, 截止时间, 采用政策快照版本
case_material    办件材料状态：id, 办件id, 材料规范id, 状态(缺失/已上传/已确认), 校验结果, 上传时间
conflict_record  冲突记录：id, 事项id, 条款A, 条款B, 冲突类型, 处置(待人工/已确认), 确认人, 确认时间
audit_log        审计日志：id, 时间, 会话id, 输入, 引用条款, 输出, 是否触发人工审核, 结果
rule_dsl         匹配规则：id, 事项id, 条件表达式, 结论(适用/不适用/需人工), 依据条款id
```

### 三个"别人做不出来"的机制（演示必须演这三个）

1. **旧政策陷阱**：同一事项检索到两份不同年份政策 → 系统检出冲突 → 标注各自生效期 → **拒绝自动裁决，要求人工确认** → 确认后写入审计日志。
2. **材料缺项检出**：按身份与事项生成必需材料清单 → 用户上传 → 系统比对 `material_spec` 检出缺失项 → 给出补办路径与依据条款。
3. **无锚点不出结论**：输出前逐条校验"条款号 + 原文片段"，未通过校验的结论**不允许出现在回答里**。

## 四、现场演示脚本（3 分钟版；视频用 5 分钟版）

| 时间 | 动作 | 要展示的东西 |
|---|---|---|
| 0:00—0:30 | 用真实身份登录（大二、非本地户籍），输入"我要办家庭经济困难认定" | 输入是身份+事项，不是聊天 |

| 2:15—2:40 | 系统检出缺 2 项，给出补办路径与截止时间 | **缺项检出**（第 2 个亮点） |
| 2:40—3:00 | 输出可打印清单 + 进度追踪页 + 审计日志页 | 闭环与可追溯 |
