## 二、闭环完整性分析（核心问题：有没有闭环？）

**结论：闭环成立，且是四层嵌套闭环。** 实测验证路径：

```
导入文件 ─→ 规则识别论断 ─→ 人工确认来源(闸门1) ─→ 确定性核验
     ↑                                                    │
     │                                              数据变更/导入更新表
     │                                                    ↓
 导出成果 ←─ 复核通过 ←─ 写入新版本 ←─ 修复预览+人工批准(闸门2)
     │              （复核失败→废弃新版本，自动回滚）        │
     └──────────── 撤销（恢复上一版本）←───────────────────┘
```

1. **流程闭环**：智能体状态机 `run → prepare → link → diagnose → ask(人工) → decide → repair → verify → done`，每个环节落盘（state.json 的 agent 字段），刷新/重启后「继续智能体待办」可恢复。实测：确认 11 项来源 → 改数据 → 11 项失效 → 批准修复 11 项 → 复核通过 → 导出文件验证内容真实更新。
2. **事务闭环**：每次变更走「复制目录 → 写新版本 → 重读复核 → 原子换指针」，复核失败自动废弃新版本（`store.repair` 中 `new_blocks != expected_blocks` 或复核未通过即 `rmtree` 回滚），磁盘实测保留 5 个版本目录，可追溯。
3. **数据闭环**：事实值与论断 refs 构成依赖图（前端有可视化），改数据只影响依赖它的论断；125→123 时「超过120万元」仍成立不误报，实测与设计文档一致。
4. **审计闭环**：每次操作留痕（audit + agent trace + history），导出包含完整 JSON 记录 + Markdown 核验报告，演示项目一个流程即产生 99 条审计记录。

**闭环中的两处断点（不影响主流程，但值得知道）：**

- **撤销只有单步**：`undo` 只恢复 `previous-state.json`（一层），连续撤销第二步即报「没有可以撤销的文件变更」。history 里明明存了多代版本，用户无法回到任意历史点，且撤销本身不可重做。
- **OCR 论断是只读支线**：图片文字确认后只做候选核验（`confirmed` 恒为 False、不可修复、不计入 repairable），这条支线没有出口闭环——发现图片内容失效后，用户只能「回原图片编辑→重新导入→重新确认」，系统没有引导这个回流路径（界面提示文字有说明，但没有一键重导入的操作指引）。

## 四、Bug 清单（按严重程度排序）

### 🔴 P0-1：大事实表导入存在千倍级性能缺陷（已验证修复方案）

**位置**：`zhilian/office.py` 第 78 行
```python
'cell': sheet.cell(rno, idx['数值'] + 1).coordinate
```
**问题**：`load_workbook(read_only=True)` 模式下，`sheet.cell()` 每次调用都从 XML 头部重新解析。行数平方级复杂度。

**实测数据**：

| 事实表行数 | 当前耗时 | 修复后 |
| --- | --- | --- |
| 499 行 | 8.64s | 0.005s |
| 1999 行（官方上限） | **129.69s** | 0.13s |

README 声称支持 2000 行，但真实用户导入 500+ 行就会以为程序卡死（前端只有「正在解析文件并识别论断」遮罩，无进度提示）。**这是影响「实用性」的第一优先级问题。**

**修复**（一行改动 + 一行 import，已验证 144 项测试全通过、输出完全一致）：
```python
from openpyxl.utils import get_column_letter   # 顶部新增
...
'cell': get_column_letter(idx['数值'] + 1) + str(rno)   # 替换原行
```

### 🟠 P1-1：Word 页眉多段落时漏发「未纳入检查」警告

**位置**：`office.py` 第 118 行
```python
if any(s.header.paragraphs[0].text or s.footer.paragraphs[0].text for s in doc.sections):
```
只检查页眉/页脚的**第一段**。实测构造「第一段空、第二段有字」的页眉 → **不产生任何警告**，用户会误以为页眉已被核验。修复：遍历全部段落 `''.join(p.text for p in s.header.paragraphs)`，页脚同理。

### 🟠 P1-2：后端支持图片直传，前端无入口（能力不对齐）

实测用 `[xlsx + png]` 直接调 `POST /api/projects` **成功创建项目**（后端上传白名单含 png/jpg/gif/webp/bmp/tiff，store.create 校验也放行），但 `web/app.js` 的上传入口（`accept=".xlsx,.docx,.pptx"`、`addFile` 过滤）只接受三种 Office 类型。OCR 功能对用户而言只能靠 Word/PPT 内嵌图片触发——**「导入一张截图」这条最自然的 OCR 使用路径在界面上不存在**。修复：前端 accept 与过滤数组加入图片扩展名，上传列表图标适配（当前 `renderUploadFiles` 中图片会错误显示为「P/PPT」图标）。

### 🟡 P2-1：`engine.check` 错误分类依赖错误文案字符串精确匹配

**位置**：`engine.py` 第 300-321 行。分类 `missing_data / source_count / source_conflict / scope_mismatch` 靠比对 `reason` 字符串常量：
```python
elif reason in ('来源缺失或数值不可计算', '增长率需要上期、本期两个事实', ...):
```
任何一处提示文案微调（比如「请」改「您」）都会让分类静默退化为 `needs_review`，前端诊断分组、报告「人工待办」分组随之错乱。**这是埋在代码里的脆弱点。** 建议：抛出带 code 的异常（`class CheckError(ValueError): code = ...`），分类走结构化字段而非文案。

### 🟡 P2-2：智能体诊断阶段写盘放大

**位置**：`agent.py` `_tool`/`_trace`。每条论断 `check_claim` 调用会全量重写 state.json 2 次。实测 20 论断项目产生 29 条 trace、30 条 audit；state.json 96KB → 诊断阶段约 60 次全量写盘。**500 论断的真实项目（state.json 约 2MB）单次诊断要写约 2GB 磁盘**，还会拖慢所有持锁请求。修复：诊断循环内累积结果、循环外一次性落盘（丢失的是「逐条崩溃可恢复」的粒度，可折中为每 50 条落盘一次）。

### 🟡 P2-3：磁盘版本目录与导出包永不清理

每次数据变更/修复/导入更新表都 `copytree` 一个新版本目录（实测一个演示流程 5 个目录）；每次导出生成 `export-{revision}.zip` 留在项目根目录。长期使用磁盘无限增长，且 README 明言「尚未实现自动版本清理」。建议：加保留策略（如保留最近 N 代 + 被历史引用的版本）或提供项目删除/归档功能——**目前连删除项目的入口都没有**，建错的项目会永远留在列表里。

### 🟡 P2-4：撤销单步、不可重做

见「闭环断点」。建议至少支持 `undo` 后 `redo`，或把 history 里的版本做成可选恢复点（版本目录都在磁盘上，数据是齐的）。

### ⚪ P3（低优先级杂项）

1. `app.py` `/api/template`：并发请求可能同时 `create_demo(folder)` 写同一批文件（单进程 RLock 之外执行），低概率损坏；建议加锁或写临时目录后 rename。
2. `store.export_local`：`shutil.rmtree(folder)` 若中途失败会留下半删除状态；且同项目同名导出直接覆盖旧目录（用户可能丢失上次导出）。
3. `engine.fmt` 对 `format(n, 'f')` 重复求值两次，微小浪费。
4. `store.list()` 逐项目读全量 state.json 只为取 4 个字段，项目多时列表变慢（演示规模无感）。
5. PPT 图表事实匹配 `f['metric'] in series.name and f['period'] == cat` 不区分主体：多主体同指标期间的事实表会让图表进入「需人工复核」（保守正确，但可以更聪明——按主体唯一性打分）。
6. 前端 `api()` 对 401 无专门处理（依赖浏览器自动弹 Basic Auth 框，Firefox/Chrome 行为一致，可接受）。

## 五、异常处理与人性化设计评价

### 异常处理（总体：优秀）

**做对了的（实测验证）**：

- 乐观锁：并发双写，后到者收到「项目已在其他窗口更新，请刷新后重试」，数据不损坏；
- SHA256 校验：源文件在分析后被外部修改 → 全部操作拒绝并提示重新导入；
- 修复复核：目标修改之外的正文变化 / 修复项重验未通过 → 自动废弃新版本；
- Office 边界：宏文件、假扩展名、超展开体积（5000 条目/80MB）、公式单元格、空/重复事实 ID 全部有明确中文报错；
- LLM 降级：模型调用失败 → 「Agent 模型降级」留痕并回退规则候选；返回的建议严格校验（ID 必须存在）、防密钥回显、**防编造数字**（解释中出现原文没有的数字即丢弃）；
- CSRF：伪造 Origin 的 POST 被 403 拦截；Basic Auth 对无凭证/错密码/畸形头全部 401；
- 路径穿越（`../../etc/passwd`）被项目 ID 白名单正则拦截。

**不足**：

- 错误提示多为「结果态」，缺「原因态」（如 30MB 超限时提示哪个文件多大、事实表缺列时提示缺哪列——部分已有，但不一致）；
- 长任务（OCR/模型最长 60 秒）期间界面无进度且**不可取消**，用户只能干等；
- P0 性能缺陷场景下（大表导入 2 分钟）无任何进度反馈，会被当成死机。

### 人性化设计（总体：良好偏优）

**亮点**：

- **双人工闸门**（来源确认与修复批准分离）+ 全部待办可分批处理、可关窗稍后继续（持久化待办恢复实测有效）；
- 修复前 diff 对照（原文/改为），下载弹窗主动提示「还有 N 项不一致」「仍有 N 项待确认」；
- 「变化不一定意味着失效」的引导文案（125→120 例子），管理用户预期；
- 数值输入草稿跨视图保持 + 「撤销未应用输入」；
- 关联规则记忆（同类论断记住上次选择，标注「已记住」且仍需人工批准）；
- OCR 结果强制人工核对、图片论断只读并在各视图显著标注；
- File System Access 写回原文件（Chrome），失败逐文件给出原因与下载降级路径；
- 移动端三级断点适配、focus-visible 键盘可达性、aria-label 部分覆盖；
- 帮助/设置弹窗把「模型能做什么、不能做什么、发送了什么」写得非常诚实（参赛答辩加分项）。

**可改进**：

- 无深色模式；
- 演示变更按钮只在 demo 项目出现（合理），但「导入更新后的 Excel」按钮用 JS 注入插在 demoChange 后面（`insertAdjacentHTML('afterend',...)`），非演示项目页面上它的位置语义有点飘；
- 论断列表无搜索框（论断多了只能靠筛选）；
- 失败 toast 5 秒自动消失，长文案读不完（错误场景建议不自动消失或延长）。

## 六、优化方向（按优先级）

### 第一优先级（直接影响可用性，建议参赛前完成）

1. **合入 P0 性能补丁**（已验证，见第四节）。
2. **暴露图片直传入口**（P1-2）：这是 OCR 功能最自然的用户路径，改动小、演示价值高。
3. **大表导入进度反馈**：前端已有 busy 遮罩，可加「已解析 N 行」或至少把 2000 行上限的建议写进模板说明。
4. **改名「表里如一」**：目前全站品牌仍是「知链」（详见第七节清单）——若决赛用新名字，务必全量替换并重新导出安装包/文档，避免评委看到两个名字。

### 第二优先级（规模化与健壮性）

5. `check` 异常结构化（P2-1），消除文案耦合。
6. agent 诊断批量落盘（P2-2），支撑数百论断的真实项目。
7. 版本目录/导出包保留策略 + **项目删除/重命名功能**（当前 UI 只有新建和进入）。
8. 撤销支持多步或版本恢复点（P2-4）。
9. 长任务（OCR/模型请求）支持取消（AbortController + 服务端协作或直接放弃结果）。

### 第三优先级（体验与功能扩展）

10. 论断/事实搜索框；深色模式；错误 toast 停留时长分级。
11. 识别能力扩展：同比/环比显式建模、「增长25个百分点」绝对增量、「占比」类论断、多系列图表（README 后续优先级已列，方向正确）。
12. Excel 公式支持（当前直接拒绝，可考虑受控地重算后采值）。
13. 多用户/权限隔离（当前共享工作空间，README 已如实声明）。
