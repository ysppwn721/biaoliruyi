## 二、我不同意的一处：排序反了

两份文档最终都落在"校园政策第一、人岗匹配第二"。但：

1. **`最终选题决策.md` 自己的矩阵把"就业材料"排在第一位**，与它的"决策建议"章节矛盾；
2. `开源项目调研与选题决策.md` 第六节写"**若已有就业指导老师、招聘数据……则可把求职方向提升为主选**"；
3. **而你在上一轮已经确认：团队能拿到就业中心 / 真实简历与招聘数据。**

**该文档自己设的升格条件已经满足了，结论却没有升格。** 建议改为：

> **主选：可验证的人岗匹配与求职教练智能体**
> **备选：校园政策与办事流程智能体**

理由：政策方向的数据谁都能自建（学校公开规章人人可得），是**无护城河的高分方向**；就业中心真实简历 + 招聘数据是**别人拿不到的资源**，配合基准校验才能做出评委无法复制的东西。政策方向仍保留为备选，因为它 25 天可交付性最高。

**但有一个岔路决定权在你们**：如果团队没有人做过招聘/HR 相关业务，或就业中心只能给"公开 JD"而没有真实投递/录用结果，那护城河消失，就**退回政策方向**。请在 48 小时内问清就业中心能拿到什么粒度的数据。

## 三、必须补的硬约束（两份文档都没有）

### 1. 时间已经不站在你们这边

两份文档都提"48 小时原型 × 3 个方向"，但**没有一份写出真实截止日**。真实节点：

- **9/19**：校内竞赛管理系统作品提交截止
- **9/20**：团队报名信息填报截止
- 9/25 校内赛定名额｜9/28 官网填报｜**10/8—10/10 官网最终提交**｜11/14 决赛答辩

**"三个方向各做一个 48 小时原型" = 6 天，正好把校内赛窗口全部烧掉，且到 9/19 一个可交付作品都没有。** 这不是"先探索再定题"，这是**弃赛**。

修正方案：**一个方向直接开工 + 其余方向各 4 小时 spike**。今天定方向，明天开始建最小闭环，9/18—9/19 交校内赛。

### 2. 会被判"无效参赛作品"而不是扣分的条款

- **公网联通性**：仅限校园网或专网访问的作品"无法评审，视为无效参赛作品"。这是作废项。演示环境必须提前买好域名/服务器，且**保证 10/21—11/14 评审期不过期**。
- **测试账号密码**：软件若设登录，**必须在设计文档显著位置注明测试账号和密码**。这条两份文档一个字没写，漏了等于专家进不去。
- **交付物五件套**（缺设计文档直接无效）：作品简介（3 图 + ≤400 字）、**软件设计文档 PDF（须用官网模板，按软件工程写全生命周期）**、完整源代码（标注原创部分）、安装包（小程序则为二维码压缩包）、MP4 视频（≤5 分钟、≤150MB）。你们的"最小可行版本"清单只提到"设计文档、源代码、演示视频"，漏了简介图、安装包和模板要求。

### 3. 开源复用带来的"原创性"反噬（这是最容易被低估的风险）

大赛要求：**原创作品、完整源代码、标注第三方开源部分、写清 AI 生成代码比例**。当作品底座是 Dify/RAGFlow 时，评委一定会问"哪部分是我们做的"。

四个具体的雷：

| 风险 | 说明 | 处置 |
|---|---|---|
| **OpenResume 是 AGPL-3.0** | 网络著作权传染：fork 后提供给用户，可能触发向用户提供源码的义务，与"只标注第三方部分"的叙事冲突 | **不要 fork**，只作交互设计参考 |
| **`job_pilot` 无 License** | GitHub 上无许可 = 保留全部权利，默认**不可复用** | 完全不可用，连抄结构都别写进文档 |
| **MaxKB 是 GPL-3.0** | 有传染性，集成进自有作品需谨慎 | 优先换 RAGFlow（Apache-2.0） |
| **Dify / FastGPT / Open WebUI 是自定义许可** | 含多租户 SaaS 限制、品牌/logo 保留条款 | 保留版权声明与 logo，用在比赛演示通常无碍，但**必须逐条读过再决定** |

**我的建议：交付物里只放 MIT / Apache-2.0 依赖**（LangGraph、RAGFlow、Reactive-Resume）；其余项目写进设计文档的"调研与借鉴"章节，**不进代码库**。这样原创性叙事最干净，也最经得起初评阶段专家的邮件/电话质询。

## 四、两条更进一步的建议

### 建议 1：政策方向的核心，不能是 RAG

`开源项目调研与选题决策.md` 一边说校园方向"现成同款项目较少"，一边列了 Dify、RAGFlow、MaxKB、FastGPT、Flowise、Open WebUI 六个成熟 RAG/工作流框架。**这恰恰说明 RAG 知识库问答的门槛已经趋零**——对手用同样的开源件两天就能搭出同类问答。

所以：**政策版本治理 + 流程状态机 + 材料闭环必须写成系统主干，RAG 只是取数层。** 演示脚本要这样走：

> 同一事项、两份不同年份的政策 → 系统检出条款冲突 → 标注生效期并**拒绝自动裁决**、要求人工确认 → 按身份生成材料清单 → 用户逐项上传 → 系统检出 2 项缺失并给出补办路径 → 输出带条款号的可打印清单。

这一段才是"别人做不出来的能力"。若演示主体仍是"问答 + 引用"，会与往届《接诉即办问答系统》（二等奖）同档。

### 建议 2：政策文件会过期，演示数据必须在 10/8 前冻结

政策是活文件。10/8 提交、10/21 起专家评审、11/14 决赛答辩——**跨度 5 周**。若期间本校政策更新，而演示环境指向实时政策库，演示会当场出错。

处置：演示用**版本冻结的政策快照** + 环境内固定日期，并在设计文档里写清"版本号 + 快照日期 + 更新机制"。这本身就是一个可以讲的技术点（版本治理），而不是缺陷。
